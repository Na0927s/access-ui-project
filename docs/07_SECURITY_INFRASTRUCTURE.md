## Overview

백엔드는 SQLite(WAL) 데이터베이스로 로그인 사용자의 계정·분석 결과를 영속화하고, 인증은 in-memory 세션 토큰으로 처리한다. 보안의 핵심은 "이미지 바이트는 저장하지 않는 것", "비밀번호는 해시로만 저장", "인가는 토큰에서만 식별", "사용자 입력을 신뢰하지 않는 것"이다.

## 데이터 처리 원칙

| 데이터 | 로그인 사용자 | 비로그인 사용자 |
|---|---|---|
| 계정(이름·이메일·ID·비밀번호 bcrypt 해시) | SQLite DB 영속화 | (가입 불가) |
| 로그인 세션 토큰 | 서버 메모리(in-memory, TTL 12h) | (없음) |
| 분석 결과 | SQLite DB 영속화(히스토리·통계) | 메모리에서만 처리(저장 안 함, 새로고침 시 소멸) |
| 분석 캐시 | SQLite DB(SHA-256 해시만 키) | 동일(개인정보 아닌 속도 향상 목적) |
| 업로드 이미지 바이트 | 서버 요청 메모리(BytesIO), 응답 후 즉시 폐기 | 동일 |
| 프론트 로그인 상태·토큰 | 브라우저 JS 메모리(Zustand) | (없음) |
| AI API 키 | 서버 환경 변수 `.env`, 코드·Git 포함 금지 | 동일 |

금지: 업로드 이미지 바이트의 DB·디스크·로그 저장, 비밀번호 평문 저장, JWT·영속 세션·세션 쿠키, user_id를 URL 경로로 받는 인가, localStorage/sessionStorage/쿠키, Zustand persist

## 인증 관련

- 비밀번호는 bcrypt 해시(rounds=12)로만 저장하고 평문으로 보관하지 않는다 (passlib 아닌 bcrypt 직접 사용).
- 로그인 성공 시 서버 메모리에 in-memory 불투명 세션 토큰(opaque token)을 발급한다. JWT가 아니며 서버 재시작 시 모든 세션이 소멸한다(영속 세션 금지).
- 보호 엔드포인트는 `Authorization: Bearer <token>` 헤더로 현재 사용자를 식별한다. `user_id`를 URL 경로로 받지 않아 타 사용자 데이터 열람이 불가하다(인가 취약점 차단).
- 계정 열거 공격 방지: 로그인 실패 시 사용자 존재 여부와 무관하게 동일한 메시지로 응답한다.
- 토큰은 브라우저 저장소(localStorage/sessionStorage/쿠키)에 쓰지 않고 프론트 메모리에만 보관한다.

## 입력 검증

### 이미지
- 프론트엔드와 서버 모두 확장자·MIME·크기(10MB) 검사
- 서버는 `Image.open` + `verify()`로 실제 이미지인지 확인
- 픽셀 폭탄 방지: `Image.MAX_IMAGE_PIXELS` 제한(예: 40MP), 초과 시 거부
- 로그에 이미지 내용·파일명 외 정보 기록 금지

### HTML/CSS (개발자 방식2)
- 사용자 HTML을 서버에서 실행하지 않는다.
- 브라우저에서 `<script>`, `<iframe>`, `<object>`, `<embed>`, `on*` 속성, `javascript:` URL 제거
- `sandbox` iframe (스크립트 비허용)에서만 렌더링, 외부 리소스 로드 차단(CSP `default-src 'none'; style-src 'unsafe-inline'`)
- 입력 크기 제한 (HTML+CSS 합계 500KB)
- 서버는 색 값과 선택자 문자열만 받으며 형식(HEX 정규식) 검증

### API 공통
- Pydantic으로 요청 스키마 검증
- 내부 예외·스택트레이스를 응답에 노출하지 않음
- CORS 허용 출처를 환경 변수로 제한
- AI 엔드포인트 요청 크기·타임아웃(20초) 제한

## AI 호출

- 키는 `ANTHROPIC_API_KEY` 환경 변수로만 주입, 없으면 AI 기능 비활성(기본 문장)
- 사용자 이미지를 AI에 보내지 않는다. 분석 결과 JSON(색·수치·문제 목록)만 전송
- 프롬프트에 "수치를 바꾸지 말고 설명만" 지시, 응답 수치는 사용하지 않음

## 인프라

- 현재 단계: 로컬 개발 (backend `:8002`, frontend `:5176`)
- 배포는 추후 결정. SQLite 파일 기반 DB이므로 Python 호스팅(백엔드, 영구 디스크 마운트) + 정적 호스팅(프론트) 또는 백엔드 단일 서빙(`STATIC_DIR`) 조합으로 배포 가능
